# 07 — i18n 独立包（`@repo/i18n`）技术设计

**状态:** Draft（待评审后实现）

**范围:** `packages/i18n`、`apps/frontend` 的 i18n 初始化/统一 hook、`apps/backend` 的私有 locale 分发

**前置约束:** 保持 Next.js Pages Router + `output: "export"` + `i18next`/`react-i18next` 现有栈，不引入 `next-i18next` 的 `serverSideTranslations`

---

## 1. 背景与目标

### 1.1 现状

| 关注点 | 当前位置 |
|--------|----------|
| locale 配置 | `apps/frontend/src/i18n/settings.json` + `settings.ts` |
| 文案源文件 | `apps/frontend/public/locales/{common,demo,todo,test}.json`，单个大 JSON，叶子是 `{ en, "zh-CN" }` |
| 构建期提取 | `apps/frontend/src/lib/i18n-static.ts` 静态 import 全部 JSON，用 `pickLocale` 按 locale 抽取 |
| 运行时 | `_app.tsx` 用 `getStaticProps` 注入的 `messages` / `fallbackMessages` 创建 i18next 实例 |
| 保密能力 | 无。所有 locale 文件都在 `public/`，构建后任何人都能直接下载 |

### 1.2 目标

1. 新建 workspace 包 `@repo/i18n`，集中管理 locale 配置、文案源文件、路径规则和编译器。
2. 文案按 JSON Path 拆分为多级目录文件：
   - `home.hero.title` → `home/hero.json` 内的 `title`；
   - `home.title` → `home/_home.json` 内的 `title`；
   - 支持无限层级，建议最多 3 层；第一层固定为 i18next namespace（通常对应页面，如 `home`；共享文案用 `common`）。
3. 构建期把拆分文件合并为 i18next 资源格式：
   - 公共 namespace 编译进前端 SSG props；
   - 私有 namespace 编译为仅后端可 import 的模块，不进入前端产物；
   - 额外生成只含 namespace 名称的 manifest，供前端识别 private，不泄漏文案。
4. 私有 locale 的 HTTP 路由完全由后端负责；`@repo/i18n` **只负责文件查找/合并**，不定义路由、不依赖 React。
5. 前端提供统一的 `useTranslation` 封装：
   - 集中配置 private API 地址和 private namespace 列表；
   - 页面调用方式与静态 locale 完全一致，不感知某个 namespace 是否 private；
   - 命中 private namespace 时自动加载，401/403 抛 `I18nAccessError`，不静默回退。
6. 保持现有路由、SEO、语言切换、Tauri adapter 行为不变。

### 1.3 非目标

- 不引入 `next-i18next`；当前 `output: "export"` 与它的 SSR 资源加载方式不兼容。
- 不实现登录/会话系统本身。私有 locale 只定义“必须经过现有 `createAuthMiddleware`”的接入点；仓库当前没有真实 auth resolver 时默认拒绝。
- 不保护页面 shell。`output: "export"` 下页面 HTML 仍然公开；本方案只保护 **locale 文案包**。
- 不迁移路由工具（`localizePath` / `stripLocalePrefix` / `replacePathLocale`）、SEO、Tauri locale 探测；这些和 Next 路由强耦合，继续留在 `apps/frontend/src/lib/i18n-utils.ts`。
- 不做复数、RTL、翻译平台对接等新 i18n 能力。
- 不实现公共 locale 的运行时分发；公共 namespace 继续走 SSG，避免额外请求和闪烁。
- 不在 `@repo/i18n` 内实现 React hook 或 HTTP 路由；这两部分分别属于前端和后端。

## 2. 关键决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 包职责 | 只做配置、源文件、路径规则、编译器和生成物 | 保持框架无关；私有路由和 React 逻辑不进入包 |
| 包名 | `@repo/i18n` | 与现有 `@repo/schemas` / `@repo/db` 命名一致 |
| 可见性粒度 | **namespace 级**（`public` / `private` 目录） | 与 i18next namespace 加载粒度一致；避免 key 级可见性带来的打包与鉴权复杂度 |
| 源文件布局 | `packages/i18n/locales/{public,private}/<namespace>/...` | 可见性一眼可见；私有文件不会误放进 `public/` |
| 编译产物 | 生成 TypeScript 模块：`generated/{manifest,public,private}` | Next SSG、Node、Cloudflare Worker 都能直接 import；无需运行时 `fs`；manifest 只含名称，可安全给前端 |
| Next 集成 | `next.config.ts` 在 dev/build phase 同步 codegen；dev 另起 `codegen --watch` | Next 16 默认 Turbopack，不支持 webpack plugin；config 负责首编，watcher 负责增量 |
| 非 Next 消费者 | backend / typecheck / test 仍前置 `pnpm i18n:build` | `next.config.ts` 只覆盖 Next；这些入口不加载 Next 配置 |
| 公共 locale | SSG 注入 | 保持现有零请求、SEO 友好的行为 |
| 私有路由 | 后端 `GET /api/i18n/:locale/:namespace` | 静态导出无法做鉴权；路由/鉴权属于后端 |
| 私有资源存放 | 编译进后端 bundle | Node 与 Worker 都能工作；避免依赖运行时文件系统或额外的 R2/KV |
| SSG 与 private | `getI18nProps` 按 manifest 跳过 private，只注入 public | 页面可以把完整 namespace 列表同时传给 `makeStaticProps` 和 `useTranslation`，不需要区分可见性 |
| 前端入口 | 单个 `useTranslation` 封装，集中配置 API 与 private namespace | 调用方只需传 namespace，不判断可见性；避免每个页面重复写 private 逻辑 |
| private namespace 来源 | `generated/manifest.ts` 的 `PRIVATE_NAMESPACES` | 与源文件同步，避免手写配置漂移；manifest 不含文案 |
| 无权限行为 | 抛 `I18nAccessError`（401/403），由 `_app` 的 `I18nErrorBoundary` 兜底 | 不静默回退到 key/默认文案；错误集中处理 |
| 加载状态 | 封装 hook 暴露 `ready` / `error` / `retry` | 与 `react-i18next` 的 `useTranslation` 形状兼容；公共页面无感 |
| `pickLocale` | 退役 | 编译器直接生成按 locale 拆好的资源；缺 key 交给 i18next `fallbackLng`，逻辑更少 |
| 默认 locale | 每个叶子必须包含默认 locale；其他 locale 可选 | 保证 fallback 链有根；缺翻译不会在默认语言下露 key |
| 生成文件是否提交 | 不提交，`.gitignore` | 源文件是唯一事实来源；Next build/dev 自动生成，其他入口用前置脚本，避免生成物漂移 |

约束：

- 包内不依赖 React / `react-i18next` / HTTP route；私有加载 hook 放在前端应用。
- 依赖保持为零（devDependencies 只需 `tsx` / `typescript` / `@types/node`）。
- `tsconfig.json` 需要 `"resolveJsonModule": true`（`settings.ts` import `settings.json`），并把 `generated/**/*.ts` 加入 `include` 以便 typecheck 覆盖生成物。

## 4. 文案源文件规范

### 4.1 目录与可见性

```text
locales/
├── public/<namespace>/...    # 可进入静态产物
└── private/<namespace>/...   # 只允许后端读取，前端运行时按需请求
```

- 根目录下只允许 `public` 和 `private` 两个目录。
- `public` / `private` 下的第一层目录是 i18next namespace（如 `common`、`todo`、`home`、`admin`）。
- 同一个 namespace **不能**同时出现在 `public` 和 `private`。需要混合可见性时拆成两个 namespace（如 `todo` + `todo-admin`）。
- 根目录下不允许直接放 `.json`；每份文案都必须属于某个 namespace。
- 非 `.json` 文件忽略（如 README）；其他根目录项报错。

### 4.2 路径 → key 映射

> 本节示例省略 `locales/` 前缀。例如表格中的 `public/home/hero.json` 实际指 `packages/i18n/locales/public/home/hero.json`；单说 `home/hero.json` 时，默认指 `public` 可见性。

设文件相对 `locales/` 的路径为：

```text
<visibility>/<namespace>/<dir...>/<file>.json
```

映射规则：

1. `namespace` = 第一层目录。
2. 若文件直接位于 namespace 根目录，且 stem 是 `_<namespace>`（namespace 索引文件），容器路径 = `[namespace]`。
3. 否则，容器路径 = `[namespace, ...dir..., fileStem]`。
4. 文件内的每个 key 追加到容器路径，得到最终 key。

示例：

| 源文件 | 容器路径 | 文件内容 | 最终 key |
|--------|----------|----------|----------|
| `public/home/_home.json` | `home` | `{ "title": ... }` | `home.title` |
| `public/home/hero.json` | `home.hero` | `{ "title": ... }` | `home.hero.title` |
| `public/home/account.json` | `home.account` | `{ "name": ... }` | `home.account.name` |
| `public/home/account/profile.json` | `home.account.profile` | `{ "name": ... }` | `home.account.profile.name` |
| `public/demo/buttons.json` | `demo.buttons` | `{ "title": ... }` | `demo.buttons.title` |
| `public/demo/buttons/row.json` | `demo.buttons.row` | `{ "variants": ... }` | `demo.buttons.row.variants` |
| `public/common/navigation.json` | `common.navigation` | `{ "demo": ... }` | `common.navigation.demo` |
| `private/admin/_admin.json` | `admin` | `{ "title": ... }` | `admin.title` |

说明：

- `_<namespace>.json` 只用于 namespace 根目录，用于“直接挂在 namespace 下”的 key；命名必须和 namespace 一致。例如 `home/_home.json` 合法，`home/_hero.json` 非法。子目录直接使用同名文件，例如 `home/account.json`（与 `home/account/` 目录共存），不写 `home/account/_account.json`。
- 普通文件与同名目录可以共存。例如 `demo/buttons.json` 提供 `demo.buttons.*`，`demo/buttons/row.json` 提供 `demo.buttons.row.*`；编译器会合并，遇到冲突报错。
- 第一层目录是 namespace；完整 key 中 namespace 不重复写入文件名。
- 支持任意深度；**建议完整 key 最多 3 段**（`namespace.group.key`），更深的路径仍可编译。
- key、目录名、文件名统一使用 `[A-Za-z0-9_-]+`；不允许 `.`、`:`、空格。`.` 会破坏 i18next 的 key separator，`:` 会破坏 namespace separator。
- `_` 前缀保留给 namespace 索引文件；目录名和 namespace 不得以 `_` 开头。

### 4.3 文件内容格式

文件内容必须是**扁平的一层对象**：

```json
{
  "title": {
    "en": "Hero Title",
    "zh-CN": "主标题"
  },
  "subtitle": {
    "en": "Hero Subtitle",
    "zh-CN": "副标题"
  }
}
```

规则：

- 每个 key 的值必须是 locale map：key 为受支持 locale，value 为字符串。
- 除 locale map 外，不允许再嵌套对象或数组。
- 一个文件可以放同一容器下的多个 key。
- 文案值原样保留，支持 i18next interpolation / plural 等语法；编译期不做转义或格式化。
- 默认 locale（当前 `en`）必须存在；其他 locale 可省略，运行时由 i18next 的 `fallbackLng` 回退到默认 locale。
- 空 locale map（`{}`）、未知 locale、非字符串值都是编译错误；空字符串 `""` 作为文案值允许。
- 不允许数组；当前项目没有数组型文案，避免引入额外路径语义。

**为什么强制扁平？**

现有文案里存在 `common.language.en` 这样的 key。如果允许文件内任意嵌套，`{ "en": "English" }` 到底是一个 locale map，还是嵌套容器，会产生歧义。路径已经决定了容器，文件内只放“key → locale map”，语义唯一。这也是 `pickLocale` 能被编译器替代的前提。

### 4.4 校验规则

编译器收集所有错误后一次性输出，任一错误都使 codegen 失败：

| 检查 | 处理 |
|------|------|
| 未知可见性目录、根目录 JSON、缺少 namespace | 错误 |
| `_<namespace>.json` 不在 namespace 根目录，或 stem 与 namespace 不一致 | 错误 |
| key / 目录 / 文件命名不符合 `[A-Za-z0-9_-]+`，或目录/namespace 以 `_` 开头 | 错误 |
| locale map 中出现非受支持 locale | 错误 |
| locale map 缺少默认 locale | 错误 |
| locale map 为空对象（`{}`）或值不是字符串 | 错误 |
| 同一完整 key 出现在两个文件/两个位置 | 错误，列出所有来源文件 |
| 同一路径既是字符串又是对象（前缀冲突） | 错误，列出冲突来源 |
| 同一 namespace 同时出现在 public/private | 错误 |
| namespace 没有任何叶子 | 错误 |

建议错误格式：

```text
i18n: 2 error(s)
  - locales/public/home/_home.json: key "hero" conflicts with locales/public/home/hero.json (string vs object)
  - locales/public/common/navigation.json: key "navigation.home" is missing default locale "en"
```

## 5. 编译器设计

### 5.1 API 与 CLI

```ts
// src/compile.ts
export type CompileOptions = {
  localesDir: string;   // 默认 packages/i18n/locales
  outDir: string;       // 默认 packages/i18n/generated
  settingsPath: string; // 默认 packages/i18n/src/settings.json；测试可覆盖
};

export type CompileResult = {
  publicNamespaces: string[];
  privateNamespaces: string[];
  filesScanned: number;
};

export function compileLocales(options?: Partial<CompileOptions>): CompileResult;
```

`compileLocales` 保持同步，并在 Next config 中直接调用。实现要求：

- 默认路径从包自身位置解析，不依赖 `process.cwd()`；
- 所有校验通过后再写文件；单文件用“临时文件 + rename”原子替换；
- 内容未变化时不重写，避免 dev 下无意义的 HMR；
- 每次调用从磁盘重新读取 `src/settings.json`；不要复用 Node `require` 缓存的静态 JSON，否则 watcher 修改 default locale / locale 列表不会生效；
- 并发调用（Next config、root dev、watcher 首编）是幂等且安全的。

`src/cli.ts` 支持 `--watch`：先编译一次，然后监听 `locales/{public,private}` 与 `src/settings.json`（default locale / locale 列表），debounce 100ms 后重新编译；编译失败只打印错误并保留上一次成功产物，不退出 watcher。实现用 Node `fs.watch`，不引入 chokidar；若目标平台的 Node 不支持递归 watch，就遍历目录分别 watch。

```ts
// src/cli.ts
// pnpm --filter @repo/i18n codegen
compileLocales();
```

- CLI 无额外参数；需要自定义目录的场景由测试直接调用 `compileLocales`。
- 默认 `localesDir` / `outDir` 通过 `import.meta.url` 解析到包根目录，不依赖进程 cwd。
- 出错时打印全部错误并 `process.exit(1)`。
- 成功后打印摘要：扫描文件数、公共/私有 namespace、输出路径。

### 5.2 算法

1. 读取 `locales/public` 与 `locales/private`，递归收集 `.json`。
2. 对每个文件按 §4.2 解析出 `visibility`、`namespace`、`containerPath`。内存树使用 `Object.create(null)` 或 `Map`，避免 `__proto__` 等 key 污染原型。
3. 读取文件内容，逐个 key 校验 locale map。
4. 写入内存树：
   - `publicTree[locale][namespace]` 或 `privateTree[locale][namespace]`；
   - 路径为 `containerPath.slice(1)` + key（相对 namespace）；
   - 写入前检查重复 key 与字符串/对象前缀冲突。
5. 检查 public/private namespace 冲突、空 namespace。
6. 对 namespace、key、locale 排序，生成 `manifest.ts`、`public/index.ts`、`private/index.ts`。
7. 原子写入：先写临时文件再 rename，避免 dev 进程读到半成品。

### 5.3 生成物

```ts
// generated/manifest.ts
// AUTO-GENERATED by @repo/i18n codegen. Do not edit.

export const PUBLIC_NAMESPACES = ["common", "demo", "todo", "test"] as const;
export const PRIVATE_NAMESPACES = ["admin"] as const;

export type PublicNamespace = (typeof PUBLIC_NAMESPACES)[number];
export type PrivateNamespace = (typeof PRIVATE_NAMESPACES)[number];
```

> manifest 只有名称，没有文案。前端可以安全 import，用来判断某个 namespace 是否 private。

// generated/private/index.ts
// AUTO-GENERATED by @repo/i18n codegen. Do not edit.

import type { LocaleResources } from "../../src/types";

类型：

```ts
export type Messages = { [key: string]: string | Messages };
export type LocaleResources = Record<
  AppLocale,
  { [namespace: string]: Messages }
>;
```

输出约定：

- 每个受支持 locale 都输出一个对象；某个 namespace 在该 locale 下没有文案时，该 locale 对象中不包含该 namespace。前端用默认 locale 回退，后端对该 namespace 返回 404。
- key/namespace 排序固定，保证生成物可复现。
- 不输出 JSON 文件。i18next 需要的资源就是普通对象；后端 API 序列化时自然变成 JSON。
- 如果后续需要把公共 locale 作为独立静态 JSON 分发给非 Next 消费方，可在 codegen 增加可选 JSON 输出；当前不默认生成，避免与 SSG 重复以及私有文件误放 `public/`。
- `packages/i18n/generated/` 加入 `.gitignore`，由 `pnpm i18n:build` 或 Next config 生成。

**为什么不用运行时读文件？**

- Next `getStaticProps` 可以读文件，但 Cloudflare Worker 没有可移植的文件系统；
- 生成 TS 模块后，前端 SSG、Node 后端、Worker 都能直接 import；
- 私有模块通过子路径隔离，构建器不会把它带进前端 bundle。

代价是增加一次 codegen；脚本和测试计划已经覆盖。

**备选方案（未采用）：** codegen 只输出私有 JSON 到后端资源目录，Node 用 `fs`、Worker 用 R2/KV 在请求时读取。优点是改文案不必重新打包后端；缺点是部署、缓存、版本原子性更复杂。当前规模选择编译进后端 bundle，API 契约不变，未来可整体替换为运行时资源读取。

### 5.4 构建脚本

根 `package.json`：

```json
{
  "scripts": {
    "i18n:build": "pnpm --filter @repo/i18n codegen",
    "dev": "pnpm i18n:build && concurrently -k -n web,worker \"pnpm --filter @repo/frontend dev\" \"pnpm --filter @repo/backend dev\"",
    "dev:web": "pnpm --filter @repo/frontend dev",
    "dev:worker": "pnpm i18n:build && pnpm --filter @repo/backend dev",
    "build": "pnpm --filter @repo/frontend build",
    "typecheck": "pnpm i18n:build && pnpm -r --if-present typecheck",
    "test": "pnpm i18n:build && pnpm -r --if-present test"
  }
}
```

`apps/frontend/package.json`：

```json
{
  "scripts": {
    "dev": "concurrently -k -n i18n,next \"pnpm --filter @repo/i18n dev\" \"next dev\"",
    "build": "next build"
  },
  "devDependencies": {
    "concurrently": "^10.0.3"
  }
}
```

`apps/backend/package.json` 的 `dev` 建议改为 watch 模式，让私有文案变化能触发后端重启：

```json
{
  "scripts": {
    "dev": "tsx --env-file-if-exists=.env --watch src/serve.ts"
  }
}
```

注意 `tsx` 4.x 不把未知 Node flag 透传给 `tsx watch` 子命令，`--env-file-if-exists` 要放在 `--watch` 之前（或使用 `NODE_OPTIONS`）；否则会被当成脚本路径。当前 `dev:worker` 跑的是 Node `serve.ts`；如果以后改用 `wrangler dev`，它不会自动监听 `packages/i18n/generated`，需要重新构建/重启 Worker。

职责划分：

- `next build` / `next dev` 由 `next.config.ts` 保证先编译，不再需要手动 `pnpm i18n:build`。
- `apps/frontend` 的 `dev` 同时启动 `@repo/i18n` watcher；修改 `locales/**` 后自动重编译，Next/Turbopack 通过 HMR 或刷新拿到新文案。
- 根 `dev` 仍先跑一次 `i18n:build`，原因是 backend 与 frontend 并发启动，backend 启动时要 import `generated/private`；这一次是启动顺序保证，不是前端构建前置。
- `dev:web` 单独运行也完整可用（Next config 首编 + watcher）。`dev:worker` 单独运行仍需前置 codegen。
- `typecheck` / `test` 不加载 Next 配置，仍由根脚本前置 `i18n:build`；直接跑 `pnpm --filter ... typecheck` 前需要先生成物。
- 生成物仍然 gitignore；如果改成提交生成物，可以删掉这些前置脚本。

root `dev`、watcher 首编、Next config 首编可能各编译一次；生成器幂等、内容未变不写文件，代价可以接受。原子替换保证并发读不会看到半成品。

### 5.5 Next.js 集成

**结论：可以，但不要用 Webpack plugin 或 Turbopack loader。**

- Next 16 默认 Turbopack，且 `next build` 也默认 Turbopack；官方明确 Turbopack 不支持 Webpack plugin。
- Turbopack loader 只能在单文件转换时返回 JS，不能 `emitFile`，`fs` 也只支持 `readFile`；本方案要生成多个模块，且 backend 也要用同一批生成物。
- 因此采用“**Next config 首编 + 独立 watcher 增量**”，不依赖 bundler 私有 API，Webpack/Turbopack 都能工作。

`apps/frontend/next.config.ts` 改为 config function：

```ts
import type { NextConfig } from "next";
import {
  PHASE_DEVELOPMENT_SERVER,
  PHASE_PRODUCTION_BUILD,
} from "next/constants";
import { compileLocales } from "@repo/i18n/compile";

export default function config(phase: string): NextConfig {
  if (
    phase === PHASE_DEVELOPMENT_SERVER ||
    phase === PHASE_PRODUCTION_BUILD
  ) {
    compileLocales();
  }

  return {
    reactStrictMode: true,
    output: "export",
    trailingSlash: true,
    images: { unoptimized: true },
    distDir: process.env.NEXT_DIST_DIR || ".next",
    transpilePackages: ["@repo/lib", "@repo/schemas", "@repo/i18n"],
    async rewrites() {
      return {
        beforeFiles: [
          {
            source: "/api/:path*",
            destination: "http://localhost:8787/api/:path*",
          },
        ],
      };
    },
  };
}
```

要点：

- Next 的 config loader 支持函数形式；这里用同步函数，`compileLocales()` 本身就是同步的。
- phase 只在 `next dev` / `next build` 触发，`next start` 等命令不写工作区。
- `@repo/i18n/compile` 是 Node-only 子路径；Next 的 config TS 转译器会通过 `require` hook 处理 workspace 的 `.ts` 入口。实现时先验证这一点；若某个 Next 小版本不处理，退回 `apps/frontend` 的 `predev` / `prebuild` 一行 codegen，架构不变。
- `compile.ts` 的依赖在模块顶层静态 import；不要在 `compileLocales` 内动态 import，因为 Next config 的 require hook 在 config 模块加载后会注销。
- 默认路径从 `compile.ts` 所在目录解析（CJS 下用 `__dirname`）；不要依赖 `import.meta.url`，因为 Next config 默认按 CJS 转译。
- `transpilePackages` 增加 `@repo/i18n`，让 Turbopack 编译并 watch `packages/i18n` 下的源码和生成物。
- `generated/` 在 `getStaticProps` 的 import 链上，Turbopack 会把它当依赖；watcher 改写后触发重新编译。若某次只改了 private locale，Next 页面不会变（private 不在 SSG），backend 的 `tsx watch` 会重启并加载新 bundle；浏览器里已缓存的 private bundle 需要刷新页面才会重新请求。
- 如果确认 HMR 没有跟随 workspace 生成物，先刷新页面；仍不更新再检查 `turbopack.root` 是否需要指向 monorepo 根。当前仓库根有 `pnpm-lock.yaml`，通常能自动推断。

**备选（未采用）：** 使用 `next dev --webpack` / `next build --webpack`，在 `webpack(config, { dev })` 里注册 plugin，在 `beforeCompile` / `watchRun` 调 codegen，并把 `locales/**` 加进 `compilation.fileDependencies`。它能在单进程内完成 build + watch，但放弃 Next 16 默认的 Turbopack，且 build 也要显式 `--webpack`，对当前项目不划算。

### 5.6 备选：直接 import JSON

可以，但要区分三种做法。

#### A. 每 locale/namespace 一个 JSON（可行，不需要 codegen）

```text
packages/i18n/locales/public/en/home.json
packages/i18n/locales/public/zh-CN/home.json
packages/i18n/locales/private/en/admin.json
...
```

每个文件就是 i18next 的 namespace 内容：

```json
{
  "hero": { "title": "Hero Title" },
  "account": { "profile": { "name": "Name" } }
}
```

前端直接静态 import：

```ts
import enHome from "@repo/i18n/locales/public/en/home.json";
import zhHome from "@repo/i18n/locales/public/zh-CN/home.json";

export const PUBLIC_RESOURCES = {
  en: { home: enHome },
  "zh-CN": { home: zhHome },
};
```

- Next/Turbopack、tsx、Wrangler 这些构建/运行时都支持静态 JSON import。
- 需要在 `package.json` 的 `exports` 暴露 `./locales/public/*` / `./locales/private/*`（或把 JSON 放在可解析路径），否则包外 import 不到。暴露 private 后，前端仍可能误 import；需要 ESLint/grep 约束，或把 private 放到单独的子包。
- 前端/backend 的 tsconfig 需要 `resolveJsonModule: true`（前端已是；backend 需确认），否则类型检查不认 JSON import。
- 不需要编译器或 Next config codegen；新增 key 只改对应 namespace 文件，新增 namespace 才需要改 index（手写或一次性脚本生成）。前端 hook 仍需要一份 private namespace 名称列表：可以手写 names-only 列表，或只对这份小文件做 codegen；不要把 private 资源 index import 到前端。
- 只在 `getStaticProps` / backend import 资源 JSON；客户端只接收序列化后的当前 locale messages，不要从组件 import `PUBLIC_RESOURCES`。
- 代价：放弃“按 key 拆文件”；每个 locale/namespace 一个文件，文件更大，多人同时改同一 namespace 更容易冲突；新增/修改一个 key 要同时改多个 locale 文件（当前 per-key 文件把同一 key 的各 locale 放在一起）。
- 这是“简化优先”时最干净的方案。

#### B. 保留按 key 拆文件，直接 import 原始 JSON（不能省掉索引/合并）

- Next 16 Turbopack 只支持静态 JSON import，不支持目录 glob；`require.context` 是 Webpack-only，`import.meta.glob` 是 Vite-only。
- 源文件是 `key -> { locale: value }`，i18next 需要 `locale -> namespace -> key`；直接 import 拿到的是原始对象，仍需要路径解析和合并。
- 一个源文件含所有 locale，直接 import 会把所有 locale 带进 bundle；private 文件一旦被前端 import 就会泄漏。
- Worker 不能 `fs.readdir`，静态 import 仍需要一份文件索引；所以“直接 import”并没有去掉 codegen/索引，只是把合并推迟到运行时。

#### C. 保留编译器，但输出 JSON（可行，收益有限）

- 生成 `generated/public.json` / `private.json` / `manifest.json`，Next/backend 直接 import JSON。
- codegen 仍然存在；只是把生成物从 TS 换成 JSON，避免生成 TS 代码和相对类型 import。
- 需要给 JSON 加类型断言或生成 `.d.ts`；不会减少编译/监听流程。

**结论：** 当前需求是“按 key 拆文件 + public/private + Worker”，直接 import 原始 JSON 不能零成本替代编译器：仍需文件索引、路径解析和合并。如果愿意放弃按 key 拆文件，A 是最简方案。否则保留 codegen；C 只是输出格式变化，不是流程简化。

## 6. 运行时设计

### 6.1 公共 namespace：SSG

`apps/frontend/src/lib/i18n-static.ts` 改为：

```ts
import {
  DEFAULT_LOCALE,
  isSupportedLocale,
  SUPPORTED_LOCALES,
  type AppLocale,
  type Messages,
} from "@repo/i18n";
import {
  PRIVATE_NAMESPACES,
  PUBLIC_NAMESPACES,
} from "@repo/i18n/generated/manifest";
import { PUBLIC_RESOURCES } from "@repo/i18n/generated/public";

export async function getI18nProps(
  ctx: StaticPageContext,
  namespaces: string[],
): Promise<I18nProps | null> {
  const locale = getLocaleFromContext(ctx);
  if (!locale) return null;

  const messages: Messages = {};
  const fallbackMessages: Messages = {};

  for (const ns of namespaces) {
    // private namespace 跳过：由运行时统一 hook 加载，页面不需要区分。
    if ((PRIVATE_NAMESPACES as readonly string[]).includes(ns)) continue;

    if (!(PUBLIC_NAMESPACES as readonly string[]).includes(ns)) {
      throw new Error(`[i18n] Unknown namespace "${ns}"`);
    }

    messages[ns] = PUBLIC_RESOURCES[locale]?.[ns] ?? {};
    fallbackMessages[ns] = PUBLIC_RESOURCES[DEFAULT_LOCALE]?.[ns] ?? {};
  }

  return { locale, messages, fallbackMessages };
}
```

- `getStaticPaths`、`makeStaticProps`、`getLocaleFromContext` 保持不变。
- `pickLocale` 及其测试删除；编译器已经完成按 locale 抽取。
- 原来的 `MESSAGES` 静态 import 和 `public/locales/*.json` 删除。
- **页面可以把同一 namespace 列表同时传给 `makeStaticProps` 和 `useTranslation`**：`getI18nProps` 只注入 public，private 由统一 hook 在运行时加载。页面这层不需要知道哪个是 private。
- 只有既不在 public、也不在 private manifest 中的 namespace 才会在构建期报错（通常是拼写错误）。
- 私有页面仍应把 `common` 放进 `makeStaticProps` 的 namespace 列表：全局 `Layout` 和 `I18nErrorBoundary` 的无权限提示都依赖公共 `common`。

### 6.2 私有 namespace：动态加载总览

```text
页面/组件
  └─ import { useTranslation } from "@/lib/i18n"
       useTranslation(["common", "admin"])
            ├─ common 已在 SSG 注入的 i18next resources 中 → 直接可用
            └─ admin ∈ PRIVATE_NAMESPACES
                 └─ 前端 private loader
                      ├─ 命中缓存 → addResourceBundle
                      └─ 未命中 → fetchPrivateLocale(privateApiBaseUrl, locale, "admin")
                           └─ GET /api/i18n/:locale/admin
                                └─ createAuthMiddleware → PRIVATE_RESOURCES
```

关键边界：

- `@repo/i18n` 不定义 `/api/i18n/...` 路由；路由由 `apps/backend` 负责。
- 前端只配置 API 基地址；loader 通过注入的 `fetchBundle` 访问，不关心后端框架。
- 页面不判断 namespace 可见性；统一 hook 通过 manifest 判断。

### 6.3 前端 private loader

位置：`apps/frontend/src/lib/i18n/private-loader.ts`（**不在 `@repo/i18n` 包内**）。

```ts
export type I18nResourceStore = {
  hasResourceBundle(lng: string, ns: string): boolean;
  addResourceBundle(
    lng: string,
    ns: string,
    resources: Messages,
    deep?: boolean,
    overwrite?: boolean,
  ): void;
  removeResourceBundle(lng: string, ns: string): void;
};

export type BundleFetcher = (
  locale: AppLocale,
  namespace: string,
  signal?: AbortSignal,
) => Promise<Messages>;

export type PrivateLocaleLoader = {
  load(
    store: I18nResourceStore,
    locale: AppLocale,
    namespaces: readonly string[],
    signal?: AbortSignal,
  ): Promise<void>;
  clear(store?: I18nResourceStore): void;
};

export function createPrivateLocaleLoader(options: {
  fetchBundle: BundleFetcher;
  fallbackLocale?: AppLocale;
}): PrivateLocaleLoader;
```

行为：

1. 对每个 namespace：
   - 当前 locale 已有 bundle → 跳过；
   - 否则请求当前 locale；
   - 若 `fallbackLocale !== locale` 且默认 locale 在 store 中还没有该 namespace → 同时请求默认 locale，保证 `fallbackLng` 可用。
2. 成功后以 `addResourceBundle(locale, ns, data, true, true)` 注入；默认 locale 同理。
3. 同一 `locale:namespace` 的并发请求去重；成功结果进入内存缓存；失败不缓存，允许重试。
4. loader 记录已经注入过的 `locale:namespace`。
5. `clear()` 清空缓存并递增 generation；旧 generation 的 in-flight 响应直接丢弃，避免登出后旧请求把私有文案写回。
6. `clear(store)` 额外对已记录的所有 `locale:namespace` 调用 `removeResourceBundle`，用于登出/用户切换；不传 `store` 时只清缓存。
7. `load()` 的 `AbortSignal` 可选；abort 不写缓存、不注入。hook 在卸载或 locale 切换时 abort 旧请求。

> 这一段是前端实现细节；`@repo/i18n` 只提供编译后的私有资源和 manifest。

### 6.4 统一 `useTranslation` 封装

> `createTranslationHook({ privateApiBaseUrl, privateNamespaces, fetchBundle })` 就是“`usePrivateI18N(apiUrl)`”的落地形式：工厂在模块初始化时接收 API 地址和 private namespace 列表，返回统一的 `useTranslation`。页面不再直接调用 `usePrivateI18N`。
>
> 这是对最初“每次调用传 api 地址”的调整：API 地址和 private namespace 改为集中配置，调用方只看到 `useTranslation`。

#### 6.4.1 集中配置

`apps/frontend/src/lib/api.ts` 增加唯一 API 入口，并接受配置传入的 API 基地址：

```ts
export async function fetchPrivateLocale(
  apiBaseUrl: string,
  locale: AppLocale,
  namespace: string,
  signal?: AbortSignal,
): Promise<Messages> {
  const base = apiBaseUrl.replace(/\/+$/, "");
  const res = await apiFetch(
    `${base}/${encodeURIComponent(locale)}/${encodeURIComponent(namespace)}`,
    { signal },
  );
  if (!res.ok) throw await parseError(res);
  return (await res.json()) as Messages;
}
```

`apps/frontend/src/lib/i18n/index.ts`：

```ts
import type { AppLocale, Messages } from "@repo/i18n";
import { PRIVATE_NAMESPACES } from "@repo/i18n/generated/manifest";
import { ApiError, fetchPrivateLocale } from "@/lib/api";
import {
  createTranslationHook,
  I18nAccessError,
} from "./create-translation-hook";

async function fetchBundle(
  apiBaseUrl: string,
  locale: AppLocale,
  namespace: string,
  signal?: AbortSignal,
): Promise<Messages> {
  try {
    return await fetchPrivateLocale(apiBaseUrl, locale, namespace, signal);
  } catch (error) {
    if (
      error instanceof ApiError &&
      (error.code === 401 || error.code === 403)
    ) {
      throw new I18nAccessError(namespace, error.code);
    }
    throw error;
  }
}

const i18n = createTranslationHook({
  privateApiBaseUrl: "/api/i18n",
  privateNamespaces: PRIVATE_NAMESPACES,
  fetchBundle,
});

export const useTranslation = i18n.useTranslation;
export const clearPrivateI18n = i18n.clear;
export type { I18nResourceStore } from "./private-loader";
export { I18nAccessError };
```

- `privateApiBaseUrl` 和 `privateNamespaces` 只在这里配置一次。
- `PRIVATE_NAMESPACES` 来自 codegen manifest，不需要手写；namespace 增删自动同步。新增/删除 private namespace 只需改 `locales/private`；dev 下 watcher 会自动重编译，生产由 `pnpm i18n:build` 或 Next build 生成，前端配置不用改。
- 页面/组件统一从 `@/lib/i18n` import `useTranslation`，不再直接 import `react-i18next`。

#### 6.4.2 Hook 工厂

`apps/frontend/src/lib/i18n/create-translation-hook.ts`（同一文件内还包含 `normalizeNamespaces` 与 `toError` 小工具）：

```ts
import { useEffect, useState } from "react";
import {
  useTranslation as useI18nextTranslation,
  type UseTranslationOptions,
} from "react-i18next";
import type { Namespace } from "i18next";
import {
  DEFAULT_LOCALE,
  resolveAppLocale,
  type AppLocale,
  type Messages,
} from "@repo/i18n";
import {
  createPrivateLocaleLoader,
  type I18nResourceStore,
} from "./private-loader";

type LoadState =
  | { status: "idle" | "loading" | "ready" }
  | { status: "error"; error: Error };

const INITIAL: LoadState = { status: "idle" };
const READY: LoadState = { status: "ready" };

export function createTranslationHook(options: {
  privateApiBaseUrl: string;
  privateNamespaces: readonly string[];
  fetchBundle: (
    apiBaseUrl: string,
    locale: AppLocale,
    namespace: string,
    signal?: AbortSignal,
  ) => Promise<Messages>;
  fallbackLocale?: AppLocale;
}) {
  const privateSet = new Set(options.privateNamespaces);
  const fallbackLocale = options.fallbackLocale ?? DEFAULT_LOCALE;
  const loader = createPrivateLocaleLoader({
    fetchBundle: (locale, namespace, signal) =>
      options.fetchBundle(
        options.privateApiBaseUrl,
        locale,
        namespace,
        signal,
      ),
    fallbackLocale,
  });

  function useTranslation(
    namespaces?: Namespace,
    useOptions?: UseTranslationOptions,
  ) {
    const i18next = useI18nextTranslation(namespaces, useOptions);
    const requested = normalizeNamespaces(namespaces);
    const privateRequested = requested.filter((ns) => privateSet.has(ns));
    const namespaceKey = privateRequested.join("|");
    const locale = resolveAppLocale(i18next.i18n.language);
    const [state, setState] = useState<LoadState>(INITIAL);
    const [attempt, setAttempt] = useState(0);

    useEffect(() => {
      const namespacesToLoad = namespaceKey
        ? namespaceKey.split("|")
        : [];
      if (namespacesToLoad.length === 0) return;

      const controller = new AbortController();
      setState({ status: "loading" });

      loader
        .load(i18next.i18n, locale, namespacesToLoad, controller.signal)
        .then(() => setState({ status: "ready" }))
        .catch((error) =>
          setState({ status: "error", error: toError(error) }),
        );

      return () => controller.abort();
    }, [i18next.i18n, locale, namespaceKey, attempt]);

    const effectiveState =
      privateRequested.length === 0 ? READY : state;

    // 无权限直接抛给上层 ErrorBoundary；不渲染 raw key / 默认文案。
    if (
      effectiveState.status === "error" &&
      effectiveState.error instanceof I18nAccessError
    ) {
      throw effectiveState.error;
    }

    // 用实际 resource store 派生 ready，避免切换 namespace 时出现一帧 raw key；
    // 同时等默认 locale bundle 就位，保证部分翻译能 fallback。
    const allLoaded = privateRequested.every(
      (ns) =>
        i18next.i18n.hasResourceBundle(locale, ns) &&
        (locale === fallbackLocale ||
          i18next.i18n.hasResourceBundle(fallbackLocale, ns)),
    );

    return {
      ...i18next,
      ready:
        i18next.ready &&
        (privateRequested.length === 0 || allLoaded),
      error:
        effectiveState.status === "error"
          ? effectiveState.error
          : null,
      retry: () => setAttempt((n) => n + 1),
    };
  }

  return {
    useTranslation,
    clear: (store: I18nResourceStore) => loader.clear(store),
  };
}
```

`I18nAccessError`：

```ts
export class I18nAccessError extends Error {
  readonly name = "I18nAccessError";

  constructor(
    readonly namespace: string,
    readonly status: 401 | 403,
  ) {
    super(`Missing permission for i18n namespace "${namespace}" (${status})`);
  }
}
```

说明：

- `normalizeNamespaces()`：字符串转数组；`undefined` 视为默认 `common`（公共），不触发 private 请求；数组保持顺序并去重。若未来把 `defaultNS` 改成 private，需要显式传 namespace。
- effect 依赖使用 `namespaceKey`；实现时在 effect 内由 key 重建数组或用 `useMemo`，避免 `react-hooks/exhaustive-deps` 警告。
- `state` 需要带上 `locale:namespaceKey`（或在 key 变化时重置），避免从失败的 private 集合切到另一个集合时复用旧 `error`。
- `privateRequested` 为空时，hook 行为与原生 `useTranslation` 基本一致，只多返回 `error` / `retry`。
- 非 401/403 错误（网络、500、404）通过 `error` 返回，`ready` 为 false；页面可显示重试，不抛给 ErrorBoundary。
- 401/403 立即抛 `I18nAccessError`，由 §6.5 的全局边界统一展示无权限。
- 私有页面仍需处理 `ready`（与原生 `useTranslation` 的 `ready` 相同）；公共页面通常它已经是 true，不需要改。

#### 6.4.3 页面用法

```tsx
import { useTranslation } from "@/lib/i18n";

function AdminPanel() {
  const { t, ready, error, retry } = useTranslation(["common", "admin"]);

  if (error) return <LoadError error={error} retry={retry} />;
  if (!ready) return <PageSkeleton />;

  return <h1>{t("admin:title")}</h1>;
}
```

页面不需要：

- 知道 `admin` 是 private；
- 调用 `usePrivateI18n`；
- 手写 fetch / `addResourceBundle` / namespace 列表。

公共页面写法不变：

```tsx
const { t } = useTranslation(["common", "todo"]);
```

迁移时页面通常只需要改 `useTranslation` 的 import 来源；`makeStaticProps` 的 namespace 列表可以保持不变——private namespace 会被 `getI18nProps` 跳过，运行时由同一个 hook 加载。

### 6.5 无权限错误与 ErrorBoundary

`apps/frontend/src/components/i18n/I18nErrorBoundary.tsx`：

```tsx
import * as React from "react";
import { I18nAccessError, useTranslation } from "@/lib/i18n";

function I18nAccessDenied() {
  const { t } = useTranslation(["common"]);
  return (
    <main>
      <h1>{t("common:error.accessDenied")}</h1>
    </main>
  );
}

type I18nErrorBoundaryProps = React.PropsWithChildren<{
  resetKey?: string;
}>;

export class I18nErrorBoundary extends React.Component<
  I18nErrorBoundaryProps,
  { error: unknown }
> {
  state = { error: null as unknown };

  static getDerivedStateFromError(error: unknown) {
    return { error };
  }

  componentDidUpdate(prevProps: I18nErrorBoundaryProps) {
    if (prevProps.resetKey !== this.props.resetKey && this.state.error) {
      this.setState({ error: null });
    }
  }

  render() {
    if (this.state.error instanceof I18nAccessError) {
      return <I18nAccessDenied />;
    }
    if (this.state.error) throw this.state.error;
    return this.props.children;
  }
}
```

`_app.tsx` 把页面内容包在边界内（边界放在 `I18nextProvider` 内、页面 `Component` 外；`Layout` 在更外层，导航保留）：

```tsx
const tree = (
  <I18nextProvider i18n={i18n}>
    <I18nErrorBoundary resetKey={router.asPath}>
      <Component {...pageProps} />
    </I18nErrorBoundary>
  </I18nextProvider>
);

return skipLayout ? tree : <Layout>{tree}</Layout>;
```

- `resetKey={router.asPath}` 在路由变化时清空错误状态（不 remount 整个页面）；登录/跳转后可以重新加载私有 namespace。
- 如果登录流程不改变路由，需在登录成功后显式改变 `resetKey`（例如把 auth/version 拼进 key，或 `router.replace(router.asPath)`），否则会停留在无权限页。
- 全局 `Layout` / 导航只使用公共 namespace；不要在 Layout 内消费 private namespace，否则错误边界无法覆盖。
- 需要在公共 `common` 增加 `error.accessDenied`（如 `"Access denied"` / `"无权访问"`）；可选增加 `error.loadFailed` / `button.retry` 给非权限错误态使用。

### 6.6 后端 API

新增 `apps/backend/src/routes/i18n.ts`：

```ts
import { Hono } from "hono";
import {
  DEFAULT_LOCALE,
  isSupportedLocale,
  type Messages,
} from "@repo/i18n";
import { PRIVATE_RESOURCES } from "@repo/i18n/generated/private";
import { createAuthMiddleware, type AuthResolver } from "../middleware/auth";
import type { AppEnv } from "../types";

const NAMESPACE_PATTERN = /^[A-Za-z0-9_-]+$/;

export function createI18nRoute(getAuthFromRequest: AuthResolver) {
  const route = new Hono<AppEnv>();

  route.use("/i18n/*", createAuthMiddleware(getAuthFromRequest));

  route.get("/i18n/:locale/:namespace", (c) => {
    const locale = c.req.param("locale");
    const namespace = c.req.param("namespace");

    if (!isSupportedLocale(locale) || !NAMESPACE_PATTERN.test(namespace)) {
      return c.json(
        { code: 400, message: "Invalid locale or namespace", data: null },
        400,
      );
    }

    // 请求 locale 没有该 namespace 时回退到默认 locale；整个 namespace 不存在才 404。
    const messages: Messages | undefined =
      PRIVATE_RESOURCES[locale]?.[namespace] ??
      PRIVATE_RESOURCES[DEFAULT_LOCALE]?.[namespace];

    if (!messages) {
      return c.json(
        { code: 404, message: "Locale namespace not found", data: null },
        404,
      );
    }

    c.header("Cache-Control", "private, no-store");
    return c.json(messages);
  });

  return route;
}
```

`apps/backend/src/index.ts`：

```ts
import { createI18nRoute } from "./routes/i18n";
import type { AuthResolver } from "./middleware/auth";

export type CreateAppOptions = {
  getAuthFromRequest?: AuthResolver;
};

export function createApp(options: CreateAppOptions = {}) {
  const getAuthFromRequest =
    options.getAuthFromRequest ?? (async () => null); // 默认拒绝

  // ...现有 middleware...

  app.route("/api", createI18nRoute(getAuthFromRequest));

  // ...现有 routes...

  return app;
}
```

- 默认 resolver 返回 `null`，所有私有 locale 请求得到 401；这是安全失败，不是“未配置就放行”。
- `serve.ts` 与 Worker 默认导出继续调用 `createApp()` 即可编译（默认 401）；接入真实 session 时，在 Node `serve.ts` / Worker 入口创建 app 处传入 resolver。
- 私有 namespace 不允许通过该 API 获取公共 namespace；公共 namespace 返回 404，避免两套分发路径。
- 请求 locale 缺该 namespace 时回退到默认 locale；整个私有 namespace 不存在时 404。
- 响应是裸 `Messages` 对象，与现有 API 风格一致；错误沿用 `{ code, message, data }`。
- 如未来需要 namespace 级 RBAC，路由可返回 403；前端 hook 已统一映射 401/403。

### 6.7 认证接入与登出

- `AuthResolver` 目前定义在 `middleware/auth.ts` 内部，需要导出，供 `createApp` 和路由工厂使用。
- 真实登录系统落地时，resolver 从 cookie/header 解析用户；私有 locale 与其它受保护 API 使用同一套认证。
- 登出或用户切换时：
  1. 调用 `clearPrivateI18n(i18n)`；它会清缓存，并对已加载的所有私有 namespace 执行 `i18n.removeResourceBundle(locale, ns)`；
  2. 重新渲染页面，让统一 hook 重新请求（未登录时得到 401 → `I18nAccessError` → 错误边界）。
- 当前仓库没有 auth UI，这一步作为接入要求写入实现文档，不在本任务中造一个假登录页。

## 7. 安全边界

### 7.1 必须保证

1. `PRIVATE_RESOURCES` 只出现在后端 bundle；前端源码、客户端 JS、静态 HTML、`out/` 中都不能出现私有文案。
2. 私有源文件只放在 `packages/i18n/locales/private/`，不复制到 `apps/frontend/public/`。
3. `apps/frontend/public/locales/` 迁移完成后整体删除，避免旧公共文件与新的私有文件混淆。
4. 私有 API 必须经过 `createAuthMiddleware`；无 auth resolver 时 401，不允许匿名读取。
5. 响应头 `Cache-Control: private, no-store`，避免共享缓存/CDN 缓存私有文案。
6. 登出清理客户端缓存与 i18next bundle。
7. manifest 只包含 namespace 名称，不包含任何文案；前端不能用它替代鉴权。

### 7.2 构建期检查

在 CI 或 `pnpm build` 后执行：

```bash
# 用私有 namespace 中的哨兵字符串检查泄漏
grep -R "PRIVATE_I18N_SENTINEL" apps/frontend/out apps/frontend/.next/static 2>/dev/null && exit 1 || true
```

建议把哨兵字符串放进一个测试专用的私有 namespace，或使用构建脚本检查 `PRIVATE_RESOURCES` 的某个已知值。该检查应作为验收项，而不是只靠 code review。

### 7.3 明确不保证

- 已授权用户仍然可以在 DevTools / 网络面板看到私有文案；这不是 DRM，只是访问控制。
- 页面 shell、路由、页面标题等仍会暴露功能存在性；如果页面本身也是机密，静态导出架构不适用。私有页面应由页面/Seo 自行设置 `noindex`，本方案不自动处理。
- 私有文案在浏览器内存中以明文存在；XSS 仍可读取。安全边界依赖现有 Web 安全措施。
- 只验证“已登录”，不做 namespace 级 RBAC；任何已认证用户都能请求任意 private namespace。需要按角色隔离时，在路由或 auth resolver 增加授权检查，并返回 403。

通用转换规则（相对 namespace 的叶子路径 `[a, b, ..., z]`）：

- 长度 2：写 `<ns>/<a>.json`，key = `b`；
- 长度 ≥ 3：写 `<ns>/<a>/<b>/.../<y>.json`（`y` 为倒数第二段），key = `z`。

5. manifest：public/private namespace 列表正确，且不含任何 locale 文案。
6. 确定性：连续运行两次生成内容字节一致；内容未变时不改写文件。
7. 原子写入：并发调用 `compileLocales` 后所有生成文件仍是完整模块，不出现半截 JSON/TS。
8. settings 读取：修改临时 `settings.json` 的 defaultLocale 后再次调用 `compileLocales` 使用新值，证明没有复用 `require` 缓存。
9. watch：修改 fixture 后触发重编译；编译失败时保留上一次成功产物，watcher 不退出。

### 10.2 前端静态 props 测试

- 传入公共 namespace：返回当前 locale 与默认 locale 两套 messages。
- 非默认 locale 缺失 namespace：`messages[ns]` 为空对象，`fallbackMessages[ns]` 为默认文案。
- 传入私有 namespace：不报错，SSG props 中不包含该 namespace；运行时由统一 hook 加载。
- 传入未知 namespace：抛错。
- `getLocaleStaticPaths` 行为不变。

### 10.3 前端 private loader 测试

用假的 `I18nResourceStore` 与 `fetchBundle`：

- 首次加载调用 fetch（当前 locale + 默认 locale）。
- 已有 bundle 不重复 fetch。
- 并发加载同一 `locale:namespace` 只发一次请求。
- 失败不缓存；重试成功。
- `clear()` 后旧 in-flight 响应被丢弃。
- `clear(store)` 移除所有已记录的 private bundle。
- `addResourceBundle` 参数为 `(locale, ns, data, true, true)`。

当前仓库没有 React 测试渲染器，不为本任务引入新测试框架；hook 保持薄层，核心逻辑在 loader 单测覆盖，hook 行为由 §10.6 手工验收。

### 10.4 错误映射与配置测试

- `401` / `403` → `I18nAccessError`，带 namespace 和 status。
- 500 / 404 / 网络错误 → 普通 Error，不抛给 ErrorBoundary。
- `normalizeNamespaces`：字符串、数组、undefined、重复项。
- manifest 的 `PRIVATE_NAMESPACES` 与统一 hook 配置一致。

### 10.5 后端路由测试

- 默认 `createApp()`：私有 locale 请求 401。
- 注入 fake resolver 返回用户：200 + messages + `Cache-Control`。
- resolver 返回 null：401。
- 非法 locale / namespace：400。
- 公共 namespace / 未知 namespace：404。
- 请求 locale 没有该 namespace、但默认 locale 有：200，返回默认 locale 文案。

## 12. 风险与待确认

### 12.1 已识别风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 仓库没有真实 auth resolver | 私有 API 默认 401，功能无法端到端使用 | 明确 `createApp({ getAuthFromRequest })` 接入点；测试用 fake resolver；生产接入前保持默认拒绝 |
| 组件绕过统一 hook 直接 import `react-i18next` | private namespace 不会自动加载，出现 raw key | 全仓 grep + ESLint `no-restricted-imports`（可选）；只允许 wrapper 和 `_app` import `react-i18next` |
| 无 ErrorBoundary 或边界位置不对 | `I18nAccessError` 导致页面崩溃 | 在 `_app` 的 `I18nextProvider` 内、Layout 外包边界；`resetKey` 绑定路由以便重置 |
| Tauri 跨源请求的 cookie/认证 | 远程 Tauri 可能无法携带浏览器 cookie（见 docs/01） | `fetchPrivateLocale` 走现有 `apiFetch`；若使用 token，必须在同一 adapter 中附加；失败时显示错误，不降级为公开文案 |
| 私有资源全部进后端 bundle | Worker/Node 包体增大 | 当前规模可接受；未来可改为 R2/KV + 版本化资源，保持 API 不变 |
| `_app` 每次页面切换重建 i18next | 私有 bundle 丢失，可能重复请求/短暂 loading | 前端 loader 内存缓存 + hook 就绪门；未来可评估稳定 i18next 实例 |
| `addResourceBundle` 不触发 react-i18next 重渲染 | 文案加载后 UI 不更新 | hook 本地 state/revision 强制重渲染 |
| 私有页面未处理 `ready` | 首次渲染短时 raw key | 文档示例强制 `if (!ready) return skeleton`；code review 检查 |
| 生成物未提交、CI 忘跑 codegen | backend/typecheck/test 找不到 `generated/*` | 前端 build/dev 由 `next.config.ts` 自动生成；backend/typecheck/test 仍由根脚本前置 `i18n:build` |
| Next 16 默认 Turbopack，Webpack plugin 不生效 | 用 plugin 做 codegen 的方案直接失效 | 不使用 Webpack plugin / Turbopack loader；Next config 首编 + 独立 watcher |
| `next.config.ts` 有写文件副作用，且可能被多次加载 | 启动变慢、并发写生成物 | 只在 dev/build phase 触发；`compileLocales` 幂等、原子写、内容未变不写 |
| watcher 与 Next config 首编重复 | 启动时多编译一次 | 生成器幂等且不写未变化文件；重复代价远小于引入 bundler 插件 |
| `settings.json` 变化未被捕获 | default locale / locale 列表仍用旧值 | watcher 同时监听 `src/settings.json`；`compileLocales` 每次从磁盘读取，不复用 require 缓存 |
| Turbopack 不跟随 workspace 生成物 | 改文案后页面不更新 | `transpilePackages` 加 `@repo/i18n`；先刷新页面，仍不更新再检查 `turbopack.root` |
| private 文案变化后 backend 仍用旧 bundle | API 返回旧文案 | backend `dev` 用 `tsx watch`；若它不跟随 workspace 生成物，手动重启或加 `--watch-path`；生产走重新部署 |
| `next.config.ts` 无法 import workspace TS 编译器 | config 加载失败 | 实现时先验证；失败则退回 `apps/frontend` 的 `predev` / `prebuild` 脚本，架构不变 |
| 前后端部署不同步 | 新页面请求了后端尚未发布的私有 namespace，得到 404 | hook 显示错误态，不渲染 raw key；发布时先部署后端或使用同一构建产物 |
| manifest 暴露 namespace 名称 | 暴露功能命名，但不暴露文案 | 接受；如需隐藏名称，可改为手动配置 private namespace 列表 |
| 文案拆分后文件数量增加 | 编辑需要定位文件 | 目录规则简单 + 编译器报错含路径；后续可加编辑器插件/脚本 |
| 误把私有 namespace 传进 `getStaticProps` | 会被跳过，不会泄漏；若页面绕过统一 hook 直接使用 `react-i18next`，会显示 raw key | `getI18nProps` 按 manifest 跳过 private + 全仓 grep 强制统一 hook + 泄漏检查 |

### 12.2 实现前需要确认

1. **真实 auth resolver 从哪里来？** 当前仓库只有 `createAuthMiddleware` 抽象，没有 session/token 实现。本文建议 `createApp({ getAuthFromRequest })`，默认拒绝；需要确认未来登录系统是否按此接入。
2. **私有可见性是否只到 namespace 级？** 本文按 namespace 设计。如果同一个 namespace 内既有公开又有保密文案，需要拆 namespace；请确认可接受。
3. **生成文件是否允许不提交？** 本文推荐 gitignore：前端 build/dev 由 `next.config.ts` 自动生成，backend/typecheck/test 由根脚本前置。如果部署流程只读或不能执行 codegen，需要改为提交 `generated/` 或在 CI 固定生成。
4. **无权限时是否接受“抛 `I18nAccessError` + 全局错误边界”的交互？** 本文按此设计；如果希望页面自行处理而非抛错，可把 hook 改为返回 `error`，但调用方必须显式检查。
5. **是否愿意放弃按 key 拆文件？** 如果更看重“零 codegen”，可以改成每 locale/namespace 一个 JSON 直接 import（§5.6 A），代价是单文件变大、同一 namespace 的并行编辑更容易冲突。当前设计保留按 key 拆文件，因此保留编译器。
